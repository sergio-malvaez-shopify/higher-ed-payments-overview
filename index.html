Shopify Retail Payments for Higher Education

Prepared for NICE Group · Shopify Partner Solutions Engineering

This page confirms what Shopify's platform supports today for campus retail payments, and shows how Watchman's integration patterns map onto those native capabilities — combining standard credit/debit, campus cards, and account-based tenders (bursar, sponsored accounts, departmental, payroll) into a single point-of-sale workflow.

The goal: show that the integrations Syatt and Watchman have built are grounded in features Shopify supports and documents today — not experimental workarounds.

01 · What Shopify Supports Today

Four native capabilities, no custom plumbing

Every integration case below is built entirely on features Shopify already ships and documents — nothing here depends on an undocumented API or a one-off exception.

Custom Payment Type

A POS order can be closed against a payment method Shopify Payments doesn't process — used for terminals or account systems managed by a third party, like Watchman.

Managing payment methods for Shopify POS →

Split Payment

A single order can be closed with more than one tender — e.g. part standard card + part campus account. Supports multiple and partial payments.

Multiple & partial payments on Shopify POS →

POS UI Extensions

Custom tiles and actions inside the native POS interface, used to trigger eligibility checks and campus-specific tenders without leaving the checkout flow.

POS UI Extensions overview →

Scanner API

Reads barcodes and QR codes only, for account lookups (e.g. a barcode-based student ID). It does not read magnetic-stripe or chip card data — no POS UI Extension API does.

Scanner API reference →

Note on scope

Shopify doesn't currently offer a Retail Payments Partner Program that would let a third-party processor plug directly into a Shopify terminal. That's why any physical campus card tap happens on a separate terminal — that's a platform-level boundary, not a gap in Watchman's integration. There's no confirmed date for if or when that changes, so this document focuses only on what's available today.

02 · How It Fits Together

One middleware layer, every case

Watchman sits between Shopify and the university's systems of record, regardless of which of the five payment types is in play. Shopify closes every order the same way at checkout — via a Custom Payment Type or a Split Payment — so from a reporting and inventory standpoint, every campus transaction looks the same to Shopify.

→

The POS UI Extension tile is the only thing the cashier touches directly. Tapping it fires an automatic call to Watchman to check eligibility — that never touches a second terminal, regardless of payment type. Only for Campus Cards does Watchman wake a second, third-party terminal (Clover is the validated option today) for the physical tap or swipe; for the other four payment types, Watchman posts straight to the relevant campus system and no second terminal is involved at all. Either way, the cashier's last step is always back on Shopify POS: select the Custom Payment Type — alone, or as the second leg of a Split Payment.

03 · Integration Paths, Case by Case

Six payment types, one pattern

Every case below reduces to the same shape: cashier taps a Watchman tile, Watchman checks something, and Shopify POS closes the order with a Custom Payment Type. What changes is what Watchman checks — and whether a second terminal is involved.

ABC DEF
A

Campus Cards

stored-value / student ID — Transact, CBORD, Atrium

The most automated of the card-present cases — but the only one that requires a second terminal. Watchman validates eligibility and balance automatically the moment the cashier triggers the tile; the physical tap/swipe happens manually on a separate third-party terminal, since Shopify terminals don't accept third-party readers.

🖥 2 terminals Custom Payment Type + Split Payment Manual: tap/swipe + tender select High automation

How it looks in practice

Cashier

Adds items to cart as usual — normal flow, no change.

Cashier

At checkout, taps the Watchman tile. That fires an automatic background call to Watchman to check eligibility and balance — nothing to wait on yet. Watchman then wakes the second terminal (Clover).

Student

Taps or swipes their campus card on the second terminal when prompted. No extra login, app, or manual entry — the terminal confirms the payment.

Cashier

Returns to Shopify POS and selects the Custom Payment Type — as the sole tender, or as the second leg of a Split Payment — to finish the sale. The receipt looks like any other purchase.

Behind the scenes — Shopify ↔ Watchman ↔ Clover

POS UI Extension tile → automatic call to Watchman (eligibility + balance) → Watchman wakes the Clover terminal → Clover confirms payment back to Watchman → Watchman settles with the campus card system (Transact, CBORD, or Atrium) → cashier marks the order paid via Custom Payment Type. Shopify never touches the card data or the terminal directly — Watchman is the only thing bridging both sides. This portion isn't processed by Shopify Payments, so there's no Shopify fee on it, but the order, line items, and reporting stay fully intact in Shopify.

Note on mag stripe & PCI compliance

  • No POS UI Extension API — Scanner, Device, or PinPad — can read a magnetic stripe directly. The Scanner API only reads barcodes and QR codes. That holds even if the campus card is stored-value only — it's a platform boundary, not a Watchman gap.
  • If the card is co-branded with Visa/Mastercard, the stripe also carries cardholder data, and PCI DSS blocks that data from reaching a third-party app like Watchman directly. Either way, the swipe happens on the second, PCI-certified terminal (Clover), which encrypts the card at capture and only passes Watchman a confirmation — never the raw card data.
  • If the card also carries a barcode, there's a lighter option: scan it with Shopify's native Scanner API instead of swiping. A barcode is an account lookup, not cardholder data, so it needs only the one Shopify POS terminal — worth confirming per campus, since it can remove the second terminal for that case entirely.
B

Bursar Billing

the highest-volume payment type at most campus stores

The simplest integration, since there's no physical card to present. Watchman checks the student's bursar account and posts the charge directly to the SIS; the cashier only confirms identity and selects the Custom Payment Type.

🖥 1 terminal Custom Payment Type Manual: confirm student ID/account High automation

How it looks in practice

Student

Provides student ID — physical card or number.

Cashier

Taps the Watchman tile, enters or scans the student ID. Watchman automatically pulls the bursar account status and balance right in the tile's modal — no second terminal, no waiting on hardware.

Cashier

Confirms the student's identity, selects the Custom Payment Type for Bursar Billing, and marks the order paid. The charge shows up on the bursar bill next cycle.

Behind the scenes — Shopify ↔ Watchman ↔ SIS

POS UI Extension tile → automatic call to Watchman → Watchman checks and posts against the SIS (Banner, Colleague, Workday Student, Jenzabar, PeopleSoft) → Shopify POS closes the order manually via Custom Payment Type. One terminal, one continuous background call — no external hardware involved.

C

Sponsored Accounts Management (SAM)

billed to a third-party sponsor, not the student

Same pattern as Bursar Billing, but the charge is validated and billed against a third-party sponsor account (e.g. VA Chapter 31, athletics, a department) instead of the student directly. Watchman supports 1,000+ sponsor configurations.

🖥 1 terminal Custom Payment Type Manual: confirm sponsor/account High automation

How it looks in practice

Student

Provides the sponsor reference or authorization code — often doesn't need to know payment details at all, since the sponsor is billed directly.

Cashier

Taps the Watchman tile, selects or enters the sponsor account. Watchman validates the sponsor's authorization and remaining limit automatically.

Cashier

Confirms, selects the Custom Payment Type for the sponsored account, and marks the order paid.

Behind the scenes — Shopify ↔ Watchman ↔ Sponsor System

POS UI Extension tile → automatic call to Watchman → Watchman validates and posts against the third-party sponsor system → Shopify POS closes the order manually via Custom Payment Type. One terminal, no external hardware involved.

D

Departmental Charges

university department purchases

Department purchases post to the SIS/ERP the same way — no physical card, single terminal.

🖥 1 terminal Custom Payment Type Manual: confirm department code High automation

How it looks in practice

Buyer

Usually a department representative rather than a student — provides the department code or authorization at checkout.

Cashier

Taps the Watchman tile, enters the department code. Watchman checks the department's budget and authorization automatically.

Cashier

Confirms, selects the Custom Payment Type for Departmental Charges, and marks the order paid.

Behind the scenes — Shopify ↔ Watchman ↔ SIS/ERP

POS UI Extension tile → automatic call to Watchman → Watchman validates and posts against the SIS/ERP (Banner, Colleague, Workday, Jenzabar, PeopleSoft) → Shopify POS closes the order via Custom Payment Type. One terminal, no external hardware involved.

E

Employee Payroll Deduction

e.g. employee computer purchase programs

Employee purchase programs post to payroll/HR instead of the SIS, but the POS-side flow is identical to Bursar Billing.

🖥 1 terminal Custom Payment Type Manual: confirm employee ID High automation

How it looks in practice

Employee

Provides their employee ID at checkout.

Cashier

Taps the Watchman tile, enters the employee ID. Watchman checks payroll eligibility automatically in the background — no waiting on hardware.

Cashier

Confirms, selects the Custom Payment Type for Payroll Deduction, and marks the order paid. The charge is deducted from a future paycheck instead of being paid on the spot.

Behind the scenes — Shopify ↔ Watchman ↔ Payroll/HR

POS UI Extension tile → automatic call to Watchman → Watchman checks and posts against the Payroll/HR system (e.g. Workday, ADP, PeopleSoft) → Shopify POS closes the order via Custom Payment Type. One terminal, no external hardware involved.

F

Combined / Split Tender

any case above + a standard credit/debit card, same sale

The cashier closes the order in two tenders — first the standard card via Shopify Payments, then the remaining balance via the relevant Custom Payment Type.

🖥 1 or 2 terminals Split Payment + Custom Payment Type Manual: select 2 tenders in sequence Depends on 2nd tender

How it looks in practice

Cashier

Starts Split Payment on Shopify POS.

Cashier + Student

Process the first tender (standard card) natively through Shopify Payments — same as any other sale, no tile needed.

Cashier + Student

For the second tender (whichever campus payment type applies), the cashier taps the Watchman tile and follows that case's flow — one sale, two tenders, nothing extra to remember or sign twice.

Behind the scenes — Shopify ↔ Watchman

Shopify Payments settles the first tender end-to-end on its own. Watchman handles the second tender exactly as it would if that were the only tender on the ticket — automatic eligibility check, and (only for Campus Cards) the terminal hand-off described in Case A. Shopify POS reconciles both into a single closed order via Split Payment.

05 · What's Confirmed vs. What's Still In Progress

Where the platform stands today

Confirmed & validated today

  • ✓Custom Payment Type and Split Payment are native, documented Shopify POS features — not a workaround built by Syatt or Watchman.
  • ✓The architecture works end-to-end conceptually for all five payment types; Watchman is the single middleware layer regardless of case.
  • ✓Clover is the validated third-party terminal for the Campus Card path.
  • ✓No POS UI Extension API can read a magnetic-stripe card directly — a platform-level boundary, not a Watchman gap, and the technical reason the physical swipe for Campus Cards has to happen on the second terminal.

Still in progress

  • …A formal demo / proof-of-concept for the two-terminal Campus Card flow.
  • …Complex financial-aid rules for California state schools (pecking-order / category restrictions) aren't supported yet.
  • …Native device/screen control on a third-party terminal — letting a student choose their tender directly on the card reader — isn't available today and isn't on a committed roadmap.
